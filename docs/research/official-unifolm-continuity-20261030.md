# 공식 UniFoLM-WLA의 chunk·IK 연속성 공개 근거 조사

조사일: 2026-10-30 KST. 범위: 공식 `unitreerobotics/unifolm-wla`의 공개 코드와 문서. 로봇 연결, 추론 실행, 원격 서버 접근·변경은 하지 않았다.

## 결론과 근거 경계

공개된 공식 WLA 코드에서 확인되는 것은 **관측 하나로 전체 EE action chunk를 만드는 stateless 서버와, 저장된 episode로 그 서버를 평가하는 offline client**이다. 실제 로봇의 chunk 소비 스케줄러, EE→IK, IK previous-solution warm-start, 관절 보간, DDS publish loop, WBC 주기 분리는 이 저장소에 공개되어 있지 않다. 따라서 “공식 WLA 실로봇은 이미 이렇게 매끄럽게 처리한다”라는 구체적인 주장은 현재 근거로 만들 수 없다. 공식 문서도 공개 client를 실로봇 실행기로 설명하지 않고 local episode의 ground truth 비교 도구로 설명한다. [공식 server 설명](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/docs/train_action_expert_en.md#L146-L168)

공식 WLA README에는 training/fine-tuning/model/dataset 공개 항목이 있지만, 별도 실로봇 배포 저장소 링크나 deployment “coming soon” 선언은 없다. 서버 주석의 `robotdeploy policy_server.py`와 CLI 설명의 `unitree_rl_wbc client protocol`은 외부 실행기 존재를 암시하는 이름일 뿐 공개 배포 코드를 제공하지 않는다. 확인 시 `unitreerobotics/robotdeploy`와 `unitreerobotics/unitree_rl_wbc` GitHub API 조회는 모두 404였다. **404는 비공개·삭제·미존재를 구별하지 못하므로 “closed source 확정”이라고 쓰지 않는다.** 조사한 공식 공개 tree에서 실제 client를 확인하지 못했다는 표현이 정확하다. [README 공개 계획](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/README.md#L32-L56), [server의 외부 이름 참조](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/action_server_wbc_msgpack_unitree.py#L361-L413), [공개 전체 tree API](https://api.github.com/repos/unitreerobotics/unifolm-wla/git/trees/a20c36800caf6cf864d0f859e00a63f99e985e98?recursive=1)

## 서버의 실제 호출 흐름

1. 연결 직후 metadata를 한 번 보내고, `get_action` 수신 시 동기 `self.get_action(msg["obs"])`를 호출한 뒤 응답한다. 이 handler 안에 실행 deadline·age 보상·이전 chunk와의 병합은 없다. `policy_reset` 등은 빈 응답 또는 `None`; `obs_chunk`는 예측·버퍼 갱신 없이 `continue`한다. 이는 스트리밍 관측 메시지를 이용한 별도 예측 갱신이 이 서버에는 없음을 뜻한다. [handler 363–403행](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/action_server_wbc_msgpack_unitree.py#L363-L403)
2. 관측 배열에 시간축이 있으면 `_last_frame`으로 마지막 행/이미지를 사용한다. EE state는 xyz+rot6d 그대로 unified state에 넣는다. 각 필드가 같은 capture timestamp인지 검사하는 로직이나 camera/state 동기화 보장은 없다. [last-frame 함수](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/action_server_wbc_msgpack_unitree.py#L121-L128), [state 및 example 생성](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/action_server_wbc_msgpack_unitree.py#L212-L281)
3. 현재 요청의 image/state/instruction으로 `model.predict_action`을 한 번 호출한다. 이전 action prefix나 이전 IK solution은 인자로 전달하지 않는다. action head는 요청마다 `torch.randn`으로 전체 trajectory를 초기화하고 flow-matching integration으로 생성한다. 이 경로에는 이전 chunk prefix 고정이나 temporal ensembling 코드가 없다. 동일 관측의 반복 요청도 별도 난수 초기화이므로 identical chunk를 보장하지 않는다는 것은 코드에서 도출되는 해석이다. [서버 추론](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/action_server_wbc_msgpack_unitree.py#L334-L359), [framework 전달 인자](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/unifolm_wla/model/framework/VLM4A/QwenMMDiT.py#L320-L378), [head 초기화](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/unifolm_wla/model/modules/action_model/MMDiT_ActionHeader.py#L293-L320), [integration](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/unifolm_wla/model/modules/action_model/MMDiT_ActionHeader.py#L335-L350)
4. unnormalize 뒤 요청 때 받은 좌우 EE state를 각각 anchor로 쓰고 **chunk의 모든 상대 pose를 같은 anchor에** `T_abs[k] = T_anchor @ T_rel[k]`로 합성한다. 앞 action을 다음 action의 anchor로 누적하는 방식이 아니다. 이후 rotation matrix를 `as_euler("xyz")`로 바꾸어 xyz+RPY action을 반환한다. 새 chunk의 anchor는 새 요청 관측의 EE이므로, anchor 변화와 예측 변화가 모두 새 absolute 목표에 반영된다. [server encode](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/action_server_wbc_msgpack_unitree.py#L285-L292), [SE(3) 합성](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/unifolm_wla_action_adapter.py#L84-L100), [RPY 변환](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/action_server_wbc_msgpack_unitree.py#L131-L142)
5. timing 로그의 `preprocess/predict/encode`는 서버 내부 구간이다. `predict` 뒤 CUDA synchronize가 있지만 network RTT나 실제 command 적용까지의 시간은 측정하지 않는다. `encode` 구간에는 debug save 호출도 들어간다. debug `prefix_len=0`, `chunk_id=0`은 고정값이므로 이것을 실행상의 chunk ID나 prefix continuity 증거로 쓰면 안 된다. [timing과 debug 필드](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/action_server_wbc_msgpack_unitree.py#L334-L359)

## offline evaluator와 smoothing을 혼동하면 안 되는 이유

공식 `eval_local_episode_wbc_msgpack_server_only.py`는 `stride` 간격으로 **저장된 dataset 관측**을 미리 만들고, 각 관측을 하나씩 send→recv한 후 앞쪽 action을 episode 배열에 stitch한다. 기본 stride는 source chunk size이며 도움말에도 non-overlapping full-chunk stitching이라고 적는다. `sleep(1/30)` 기반 실행이나 벽시계 제어는 이 과정에 없다. 따라서 “공식 로봇은 chunk 30개를 다 쓴 뒤 blocking inference한다”라고 이 평가 코드로 단정할 수 없다. [stride 설명](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/eval_local_episode_wbc_msgpack_server_only.py#L97-L99), [순차 RPC](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/eval_local_episode_wbc_msgpack_server_only.py#L145-L172), [dataset 관측 생성](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/eval_local_episode_wbc_msgpack_server_only.py#L242-L274), [앞부분 stitch](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/model_server/eval_local_episode_wbc_msgpack_server_only.py#L282-L297)

공식 processing 문서에는 component-wise linear resampling과 2초 context의 cubic B-spline resampling이 설명되어 있고 `dataloader/.../fps_utils.py`에 helper가 있다. 그러나 이 helper를 공개 inference server의 predicted action→command 경로가 호출하지 않는다. 따라서 **데이터 action-sequence resampling 규격**과 **로봇 런타임 관절 smoothing**을 구분해야 한다. 같은 FPS의 linear helper는 바로 입력을 반환한다. 현재 `single_source_dataset.py`의 미래 timestamp 구성은 실제로 `range(0,fps)`의 1초 표본이다. 함수 설명의 “B-spline enabled일 때 2초”라는 문구만으로 현재 런타임에서 spline이 활성화되었다고 판정할 수 없다. [resampling 문서](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/docs/robot_action_state_processing_en.md#L1494-L1584), [linear helper](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/unifolm_wla/dataloader/multi_source_dataset/fps_utils.py#L5-L31), [B-spline helper](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/unifolm_wla/dataloader/multi_source_dataset/fps_utils.py#L34-L83), [실제 dataset timestamp 구성](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/unifolm_wla/dataloader/multi_source_dataset/single_source_dataset.py#L120-L139)

추가 제약: 공식 문서는 공개 server protocol이 **Dex1 only**이며 WBT의 finger angles와 relative base pose를 지원하려면 확장해야 한다고 명시한다. 이름에 `WBC` 또는 `fullbody`가 있다는 것만으로 공개 server가 실로봇 전체 제어 계층을 포함한다고 해석하면 안 된다. [Dex1 범위 명시](https://github.com/unitreerobotics/unifolm-wla/blob/0a1aa87be8f775c7883fcd27216e3666ac18a8c5/docs/train_action_expert_en.md#L155-L168)

## PAOS+UniFoLM Adapter 조사에 적용할 수 있는 점

아래는 공식 동작에 대한 추가 사실이 아니라, 위 코드 경계에서 도출한 **진단 관점**이다.

- 같은 chunk 내부의 EE 목표가 이미 고정되었다면, 그 chunk를 소비하는 동안 생기는 관절해 급변은 공식 server가 매 주기 EE를 재합성해서 생긴다고 설명할 수 없다. adapter의 index 선택, frame 변환, IK 입력과 seed, solver output, publish target을 연속 추적해야 한다.
- 새 chunk 경계는 새 관측 anchor, 새 예측, 새 index 시작점이 함께 바뀔 수 있다. 이전 chunk 마지막 실행 목표와 새 chunk 첫 선택 목표를 먼저 비교한 뒤 EE가 연속인데 관절만 불연속인지 구분해야 한다.
- RPY 성분의 큰 수치 차이만으로 EE orientation의 실제 급회전을 판정하면 안 된다. 공식 server가 Euler 표현을 반환하므로 상대 회전각·회전행렬 기준의 차이도 함께 비교해야 한다.
- previous-solution warm-start나 관절 보간은 공개 WLA의 확인된 보장으로 취급할 수 없다. PAOS adapter에서 사용 여부를 따로 증명해야 한다. 필요성을 논의할 수는 있지만 “공식 배포의 재현”이라는 이름은 붙일 수 없다.
- 요청 시점 지연 여부는 observation capture/send, server receive/predict/response, client receive/select, IK start/end, DDS publish의 timestamp를 나누어야 한다. 공식 서버 timing 로그만으로 network delay 또는 WBC 끊김의 원인을 확정할 수 없다.
